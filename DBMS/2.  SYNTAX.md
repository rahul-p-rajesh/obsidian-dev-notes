## Create
```sql

CREATE TABLE users ( 
id INT PRIMARY KEY AUTO_INCREMENT, 
name VARCHAR(100), 
email VARCHAR(255) UNIQUE, 
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP 
);


CREATE TABLE products (
id INT PRIMARY KEY AUTO_INCREMENT,
user_id INT, -- foreign key 
column name VARCHAR(100), 
price DECIMAL(10,2), 
attributes JSON, 
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, 

FOREIGN KEY (user_id) REFERENCES users(id) -- link to users table 
);

DESC products; --show schema of table or DESCRIBE products

```

## Update

```sql


-- update a single column 
UPDATE products SET price = 899.99 WHERE id = 2; 

-- update multiple columns 
UPDATE products SET name = 'Gaming Laptop', price = 1299.99 WHERE id = 2;

-- update a JSON field 
UPDATE products SET attributes = JSON_SET(attributes, '$.color', 'red')
 WHERE id = 1;
```



## DELETE

```sql

DROP TABLE products; -- delete table


DELETE FROM products WHERE id = 3; --when we want to delete a row


DELETE FROM products; -- empty whole table but not optimal

TRUNCATE TABLE products; -- more optimal in emptying a table 

--Wy TRUNCATE is more optimal in 

**`DELETE` — row-by-row, logged**
- Scans the table and removes rows one at a time.
- Every deleted row generates a log entry (in Postgres: WAL; in MySQL: binlog/undo log). This is what makes it transactional and rollback-able.
- After deletion, the space those rows occupied isn't immediately returned to the OS — it's just marked as "reusable" (dead tuples in Postgres, fragmented pages in MySQL).
- Triggers fire for every row.
- If you `DELETE` all rows, the table still has all its pages allocated — you need a subsequent `VACUUM` (Postgres) or `OPTIMIZE TABLE` (MySQL) to reclaim space.
  
  
**`TRUNCATE` — metadata operation**

- Doesn't touch individual rows at all. It essentially drops the underlying data pages and replaces them with a fresh empty set — this is why it's sometimes called a "DDL operation" rather than a DML one.
- In Postgres specifically, `TRUNCATE` deallocates the data files and resets sequences (if `RESTART IDENTITY` is specified). It's O(1) with respect to row count — doesn't matter if the table has 10 rows or 10 billion.
- WAL logging still happens, but it logs the _file removal_, not individual row deletes — far less write amplification.
- Triggers do **not** fire (row-level triggers at least).
- Space is immediately returned to the OS (or the tablespace, depending on DB).

```
