
## Why do we need DB? Why not csv or text files
1. **Concurrency:** A CSV cannot handle multiple simultaneous reads and writes safely. If two users save changes at once, the last save overwrites the others — even if the edits were on different rows. A DB uses [[locks]] and [[transactions]] to coordinate concurrent access at the row level.
2. **Transactions (ACID)**: A DB can group multiple operations into a single unit that either fully succeeds or fully rolls back. CSVs have no such mechanism, so a crash mid-write can leave data corrupted.
3. **Reliability & crash recovery**
4. **Faster reads and writes**: DBs use indexes (B-trees, hash indexes) to find records in microseconds, even in tables with millions of rows. CSVs require scanning the whole file.
5. **Data integrity**: DBs enforce data types, primary keys, foreign keys, uniqueness, and custom constraints. CSVs accept any garbage you write into them.
6. Security



## Types of DB
1. Relational (Sql)
2. NoSql
### Relational
1. They are those which follows sql standards to a level
	1. **What are SQL standards?** Official specifications by ANSI/ISO that define how SQL should look and behave (syntax, data types, query semantics, etc.). Versions include SQL-92, SQL:1999, SQL:2003, SQL:2016, SQL:2023. No DB implements 100%, but the core is portable across systems.
2. Store data in **tabular format** (rows and columns) with a fixed schema.
3. Are **[[ACID compliant]]** — Atomicity, Consistency, Isolation, Durability.
4. Use predefined **relationships** between tables via foreign keys.
- Examples: MySQL, PostgreSQL, Oracle, SQL Server, SQLite.


### No Sql
1.- Each DB has its **own query language / API** — no common standard like SQL.
- Store data in **different formats**:
    - **MongoDB** → documents in BSON (binary JSON)
    - **Redis** → key-value pairs (in memory)
    - **Cassandra** → wide-column store
    - **Neo4j** → graph (nodes and edges)
- Typically have a **flexible or no schema** — fields can vary between records.
- Often trade strict ACID for **scalability and availability** (BASE model: Basically Available, Soft state, Eventual consistency).
- Better suited for **unstructured, semi-structured, or rapidly changing data**, and horizontal scaling across many servers.
